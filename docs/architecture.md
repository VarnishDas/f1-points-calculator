# Architecture

A static single-page app: Vite + React 19 + TypeScript, styled with Tailwind CSS 4, state managed by Zustand. There is no backend; all data is bundled as JSON and all computation happens in the browser.

## Module map

### Engine — `src/engine/`

Pure, framework-free functions. Everything the app knows about points and standings lives here.

- `calculateRacePoints.ts` — 2026 points tables (`POINTS_TABLE` for Grands Prix, `SPRINT_POINTS_TABLE` for sprints) and per-race points calculation. Fastest-lap points are intentionally not modeled.
- `calculateStandings.ts` — official standings from completed results only (`officialOnly` mode).
- `calculateProjectedStandings.ts` — what-if standings: official results plus the user's predictions for sessions that have not happened yet (`officialAndPredicted` mode).
- `standingsAggregation.ts` — shared aggregation core used by both modes: `aggregateChampionshipEntries` accumulates points and finishing-position counts for drivers and teams, `buildStandings` sorts them into ordered standings.
- `resolveTies.ts` — FIA championship countback: compare points, then number of 1st places, 2nd places, and so on. An app-level `fallbackOrder` keeps rendering stable when countback cannot separate entries; it is not an FIA criterion.
- `calculateWdcStatus.ts` — per-driver title status (`champion` / `inContention` / `outOfContention`). Unresolved slots are modeled in each driver's best case; if even that cannot put them ahead on points or countback, they are out.

### Store — `src/store/useCalculatorStore.ts`

A single Zustand store holding `races`, `drivers`, `teams`, and `activeDriverIds`. Imported JSON is cloned on init so the module data is never mutated. Actions:

- `updatePrediction(raceId, session, orderedDriverIds)` — write a normalized prediction for a Grand Prix or Sprint.
- `clearPredictionPosition(raceId, session, positionIndex)` — remove one predicted slot.
- `applyScenario(scenario)` — hydrate predictions from a decoded URL scenario.
- `resetPredictions()` — clear all predictions on upcoming races.

All writes go through a normalizer that drops unknown drivers, duplicate placements, and out-of-range positions, and trims sparse arrays. Sessions are only writable when `isPredictionSessionEditable` allows it (race is upcoming; sprint exists and has no official result yet).

### Utils — `src/utils/`

- `encodeScenario.ts` — serialize predictions into a versioned payload (`v: 2`, sparse `{ p, d }` entries grouped by race, split into `predictions` and `sprintPredictions`), then Base64url-encode it under the hash key `s`. Completed races are never encoded. The output is deterministic.
- `decodeScenario.ts` — parse and validate a scenario from a hash string against the current app data. Unknown race/driver ids, completed races, duplicates, and malformed payloads are filtered or rejected; v1 payloads are migrated to the v2 shape. Never throws.
- `predictionSession.ts` — `isPredictionSessionEditable`, the single source of truth for whether a session accepts predictions.
- `classification.ts` — `getClassificationSize`, the grid size derived from configured bounds (`src/config/season.ts`) and actual result data.

### Components — `src/components/`

- `PredictionWorkspace.tsx` — owns the @dnd-kit `DndContext`, sensors, and drag overlay; routes drop events to the store via helpers in `predictionDnd.ts`.
- `PredictionBoard.tsx` — desktop grid with one column per upcoming race/session (`predictionBoardColumns.ts`, `PredictionCell.tsx`).
- `MobilePredictionBoard.tsx` — per-race board for small screens (`mobilePredictionBoardState.ts`).
- `DriverPool.tsx` / `DriverTile.tsx` — draggable driver tiles.
- `StandingsPanel.tsx` — projected driver/constructor tables with WDC status badges.
- `DashboardLayout.tsx` — responsive two-pane layout with a collapsible standings panel on mobile.
- `AppHeader.tsx` — share button (copies the scenario URL) and reset control; `Footer.tsx`.

### Data — `src/data/`

Static JSON (`drivers.json`, `teams.json`, `races.json`, `metadata.json`) re-exported as typed arrays from `index.ts`, which also derives `activeDriverIds`. Files are generated by `scripts/update-data.ts` from the Jolpica-F1 API and refreshed by a scheduled GitHub Actions workflow — see [data-pipeline.md](data-pipeline.md).

### Hooks — `src/hooks/useShareableUrl.ts`

Side-effect-only hook mounted once in `App`. On load it decodes `window.location.hash` and applies the scenario to the store; afterwards it subscribes to the store and rewrites the hash with `history.replaceState` whenever predictions change.

## Data flow

1. The user drags a driver tile onto a prediction slot.
2. `PredictionWorkspace` resolves the drop via `predictionDnd.ts` and calls `updatePrediction` (or `clearPredictionPosition`) on the store.
3. The store normalizes and stores the new prediction; subscribers are notified.
4. `App` selects `races`/`drivers`/`teams` from the store and recomputes `calculateProjectedStandings` and `calculateWdcStatus` in `useMemo`.
5. `StandingsPanel` re-renders with the new standings and title statuses.

## URL share flow

- **Encode:** predictions (upcoming races only) → `encodeScenario` → JSON → Base64url → `#s=...` written to `window.location.hash` via `history.replaceState` (no history spam, cleared when empty). The header share button copies the full URL to the clipboard.
- **Decode:** on page load, `useShareableUrl` reads the hash, `decodeScenarioFromHash` validates every entry against current app data, and `applyScenario` hydrates the store. The URL is then canonicalized so stale or tampered ids are stripped.
